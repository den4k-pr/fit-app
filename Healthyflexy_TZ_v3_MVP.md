## 0. Про цей документ

Це спрощена версія ТЗ v2.0. Продуктова ідея та ключові екрани збережені. Усе, що потребує ліцензій, платіжної інфраструктури або ML-моделі, винесено у v2 (розділ 20).

Документ написаний так, щоб його можна було покласти в репозиторій як `SPEC.md` і давати AI-агенту як єдине джерело правди. Розділ 19 містить правила для AI-агента.

**Чотири принципи спрощення:**

1. **Перевірити гіпотезу, а не будувати платформу.** MVP має відповісти на одне питання: чи мотивують гроші від дитини батьків 50+ робити вправи щодня.
2. **Гроші — це облік, а не рух.** Застосунок веде баланс «скільки дитина винна батьку/матері». Реальний переказ дитина робить сама поза застосунком.
3. **Довіра замість AI.** Батьки записують короткі відео, дитина їх бачить. Автоматичної перевірки техніки у v1 немає, і застосунок не імітує її.
4. **Фіксовані правила.** Один набір з 4 вправ, одна нагорода за день, один батько на одну дитину.

## 1. Продукт і мета MVP

### 1.1 Опис

Healthyflexy («Книжка турботи») — сімейний мобільний застосунок. Дорослі діти платять батькам 50+ грошову винагороду за щоденне виконання коротких фізичних вправ. Батько/мати виконує 4 вправи (≈10–15 хв) і записує коротке відео кожної. Після виконання всіх вправ дня система автоматично нараховує винагороду. Дитина бачить прогрес у реальному часі, переглядає відео та рахується з батьком/матір'ю.

### 1.2 Основна гіпотеза

Грошова винагорода від близької людини — найсильніший мотиватор для формування щоденної звички у людей 50+. Це не абонемент і не нагадування, а сімейний договір із фінансовим зобов'язанням.

### 1.3 Мета пілоту

- 5–20 реальних сімей.
- 2–3 тижні використання.
- Збір якісного фідбеку (інтерв'ю з батьками й дітьми).

### 1.4 Критерії успіху пілоту

Усі метрики рахуються SQL-запитами по базі, окремої аналітики немає.

| Метрика | Ціль |
|---|---|
| Completion rate (виконані дні / заплановані дні) | ≥ 70% |
| Середня поточна серія (streak) по сім'ях | ≥ 7 днів |
| Сім'ї, де хоча б один переказ підтверджений батьком | ≥ 60% |
| Якісний фідбек | Мінімум 5 інтерв'ю |

## 2. Обсяг v1

### 2.1 Входить у v1

- Згода (consent), медичний дисклеймер, онбординг.
- Вхід по номеру телефону + SMS-код.
- Дві ролі: батько/мати та дитина.
- Зв'язок акаунтів через код або посилання-запрошення.
- Щоденні 4 вправи: демо, запис відео, автоматичне нарахування за день.
- Дашборд дитини: статус, баланс, відео, «Нагадати».
- План: дні тижня, ставка, час нагадування.
- Облік розрахунків: «Переказ зроблено» / «Підтверджено».
- Історія, календар, серія днів.

- Три мови: українська, польська, англійська.
- Видалення акаунта.

### 3.2 Схема

```
┌──────────────────────┐        ┌──────────────────────────────────┐
│  Expo app (iOS/And.) │◄──────►│  Supabase                        │
│  Expo Router         │  HTTPS │  • Auth (SMS OTP)                │
│  TanStack Query      │  WSS   │  • Postgres + RLS + RPC          │
│  expo-camera         │        │  • Storage (приватні відео)      │
│  expo-notifications  │        │  • Realtime (статус дня)         │
└──────────┬───────────┘        │  • Edge Functions (push, cron)   │
           │                    │  • pg_cron                       │
           │ push               └───────────────┬──────────────────┘
           ▼                                    │
   Expo Push Service ◄──────────────────────────┘
```

### 3.3 Архітектурні принципи

1. **Вся бізнес-логіка з грошима та нарахуваннями — тільки на сервері** (Postgres-функції). Клієнт ніколи не рахує й не записує баланс.
2. **Усі таблиці під RLS.** Прямі `INSERT/UPDATE/DELETE` для клієнта закриті. Зміни виконуються тільки через RPC-функції.
3. **У застосунку лише `anon` ключ Supabase.** `service_role` ключ живе тільки в Edge Functions.
4. **Один клієнт — один екран — один запит.** Без складної глобальної стейт-машини: TanStack Query для серверних даних, React Context для сесії.
5. **Потрібен інтернет.** Offline-режиму у v1 немає.
6. **Усі тексти через i18n.** Жодних захардкоджених рядків у компонентах.

## 4. Ролі користувачів

### 4.1 Батько/мати (parent), основний користувач

Людина 50–80 років, живе окремо від дітей, низький технічний рівень. Головна цінність: простота й відчуття турботи, а не контролю.

- Бачить сьогоднішні вправи в максимально простому вигляді.
- Виконує вправу за демо-відео та записує себе на камеру.
- Отримує автоматичне нарахування за виконаний день.
- Бачить баланс, серію, календар та історію розрахунків.
- Підтверджує отримання переказу від дитини.

### 4.2 Дитина (child), спонсор

Дорослий 30–55 років. Головна цінність: бачити, що батько/мати активні та здорові, без надокучливого контролю.

- Створює акаунт і запрошує батька/матір.
- Налаштовує план: дні, ставка, час нагадування.
- Бачить статус дня та переглядає відео.
- Надсилає нагадування.
- Фіксує переказ грошей («Переказ зроблено»).

### 4.3 Адміністратор

Окремої ролі й інтерфейсу немає. Команда працює через Supabase Studio та SQL.

### 4.4 Правила зв'язку

- Одна дитина ↔ один батько/мати в інтерфейсі v1. Схема БД дозволяє розширення: `parent_id` унікальний, `child_id` — ні.
- Один батько/мати може бути в одній сім'ї.
- Роль обирається один раз і не змінюється (тригер у БД це забороняє).
- Застосунок призначений для повнолітніх (18+).

## 5. Онбординг та автентифікація

### 5.1 Порядок першого запуску

`Згода → Онбординг (3 слайди) → Телефон → SMS-код → Роль → Ім'я → (батько: чекає запрошення / дитина: перший план + запрошення)`

Згода й онбординг показуються один раз. Стан зберігається локально (AsyncStorage), а після реєстрації згода записується в `profiles`.

### 5.2 Екран згоди (Consent)

Обов'язковий для GDPR. Показується один раз при першому запуску, до будь-яких інших екранів.

- Іконка 📋 і заголовок **«Перш ніж почати»**.
- Короткий опис: «Книжка турботи допомагає дорослим дітям мотивувати батьків щодня робити прості вправи».
- Блок: **«Застосунок не є медичним пристроєм і не замінює консультацію лікаря»**.
- Три чекбокси, усі обов'язкові:
  1. Розумію, що застосунок не є медичною рекомендацією.
  2. Погоджуюсь з Умовами використання та Політикою конфіденційності (посилання).
  3. Батько/мати проконсультувалися з лікарем перед початком вправ.
- Кнопка **«Прийняти та продовжити»**, активна лише коли відмічені всі три.
- Футер: «Ваші дані захищені відповідно до GDPR».

Після реєстрації в `profiles` записуються `gdpr_consent_at` і `disclaimer_seen_at`.

### 5.3 Онбординг (3 слайди)

Кнопки: «Далі» / «Почати» (останній слайд) / «Пропустити». Внизу точки-індикатори.

| Слайд | Заголовок | Суть |
|---|---|---|
| 1 | 💚 «Книжка турботи» | Що це за застосунок, одним абзацом |
| 2 | 👵 «Ви виконуєте вправи» | Батько/мати щодня робить 4 прості вправи й записує коротке відео |
| 3 | 💰 «Турбота, яка винагороджується» | Дитина платить за кожен виконаний день; ви бачите свій заробіток |

### 5.4 Реєстрація та вхід

Єдиний спосіб входу для обох ролей: **номер телефону + SMS-код (OTP)**. Паролів немає.

| Крок | Екран |
|---|---|
| 1 | Номер телефону, вибір країни (за замовчуванням Польща 🇵🇱) |
| 2 | 6-значний код з SMS (кнопка «Надіслати ще раз» через 60 секунд) |
| 3 | Вибір ролі: **«👵 Я батько/мати»** / **«👨 Я дитина»** |
| 4а | Батько/мати: ім'я (вік — необов'язково) |
| 4б | Дитина: ім'я |
| 5а | Батько/мати: екран «Чекаємо на запрошення» з полем для коду |
| 5б | Дитина: налаштування першого плану + кнопка «Запросити» |

Технічні вимоги:

- Supabase Auth, phone provider, SMS через Twilio.
- Сесія зберігається на пристрої й оновлюється автоматично; повторний вхід не потрібен.
- Для розробки використовувати тестові номери та коди в налаштуваннях Supabase Auth.
- Ліміти OTP налаштувати в Supabase Auth. У Twilio обмежити SMS до потрібних країн (Geo Permissions), щоб уникнути SMS-шахрайства та неочікуваних витрат.
- Після входу зберігаються `language` (мова пристрою, якщо це uk/pl/en, інакше en) та `timezone` (IANA, з пристрою).

### 5.5 Зв'язок акаунтів (запрошення)

1. Дитина натискає **«Запросити»**, обирає, ким їй є людина (Мама / Тато / Бабуся / Дідусь / Інше).
2. Система генерує **6-символьний код** (великі літери й цифри без схожих символів `0 O 1 I L`) і посилання виду `healthyflexy://join/ABC234` (deep link).
3. Дитина ділиться через системне меню «Поділитися»: текст із кодом і посиланням («Встанови «Книжку турботи» і введи код ABC234»).
4. Батько/мати або відкриває посилання (код підставляється автоматично), або вводить код вручну на екрані очікування.
5. Після прийняття створюється сім'я, обидва бачать свої екрани.

Правила:

- Код діє 7 днів і одноразовий.
- Нова активна пропозиція автоматично знецінює попередню невикористану.
- Батько/мати може приєднатися лише до однієї сім'ї.
- Universal Links (https-посилання, що відкриває застосунок) відкладені до v2, тому основний шлях — код.

## 6. Екрани батька/матері

Навігація: **2 таби** («Сьогодні» та «Історія»). Профіль відкривається кліком на емодзі-аватар у шапці.

### 6.1 Екран «Очікування» (немає сім'ї)

- Текст: «Попросіть дитину надіслати вам код запрошення».
- Поле для 6-символьного коду, кнопка «Приєднатися».
- Помилки простою мовою: «Код не знайдено або строк його дії минув».

### 6.2 Таб 1 — «Сьогодні»

**Шапка**

- Емодзі-аватар 👵 / 👴 (натискання відкриває профіль).
- Привітання за часом доби: «Доброго ранку» (05:00–11:59), «Добрий день» (12:00–17:59), «Добрий вечір» (18:00–04:59) + ім'я.
- Дата й день тижня.
- Велика сума: **«До отримання: €35»** (натискання відкриває таб «Історія»).

**Кільце прогресу**

- SVG-кільце: виконані / усього вправ (наприклад, 1/4). Число всередині.
- Банер під кільцем: «Виконайте всі вправи й заробіть €5 сьогодні».

**Список вправ**

- Вертикальний список карток: іконка категорії, назва, кількість повторень або час.
- Стан картки: ✓ виконано (закреслена) / кнопка **«Старт»** (поточна) / 🔒 заблоковано.
- Вправи відкриваються **послідовно**: наступна доступна після виконання попередньої.

**Спеціальні стани**

| Стан | Що показувати |
|---|---|
| День відпочинку (не в плані) | «Сьогодні день відпочинку 🌿. Наступне заняття: середа» + поточна серія |
| Усе виконано | «Сьогодні все виконано! +€5 ✅» + серія |
| Не завантажились дані | Простий екран з кнопкою «Спробувати ще раз» |

### 6.3 Потік вправи (3 фази)

Відкривається з картки «Старт».

**Фаза 1 — Демо**

- Відео-зациклена демонстрація вправи (`expo-video`, без звуку).
- Текст: «Дивіться на техніку. Запам'ятайте рух».
- Блок «⚡ Користь»: короткий текст + посилання 🔗 на джерело.
- Кнопка **«Почати вправу»**.

**Фаза 2 — Запис**

- Вмикається фронтальна камера. Червона крапка REC і таймер зворотного відліку від ліміту вправи (30 або 60 секунд, `record_max_sec`).

## 8. Бізнес-логіка

### 8.1 День (session)

- «День» — це запис у таблиці `sessions`: одна сім'я, одна дата.
- Дата рахується **за часовим поясом батька/матері** (`profiles.timezone`).
- Запис створюється при першому відкритті екрана «Сьогодні» (функція `get_or_create_today`) — лише якщо день входить у `plan_days`.
- У записі фіксуються: `exercises_total` (кількість активних вправ) і `rate` (ставка на момент створення).
- Статуси: `pending` → `in_progress` → `completed` або `missed`.

### 8.2 Нарахування

1. Кожна вправа фіксується функцією `complete_exercise` (див. розділ 14). Вона перевіряє, що вправа наступна в черзі та що день сьогоднішній і не завершений.
2. Коли `exercises_done = exercises_total`, день стає `completed`, `earned = rate`, у `ledger` створюється запис `earn` (унікальний на день, тому повтори безпечні).
3. Часткове виконання **не оплачується**.
4. Вправа без відео («Зарахувати без відео») зараховується так само, але дитина бачить позначку «без відео».

### 8.3 Пропущені дні

- Функція `close_past_days` запускається щогодини (`pg_cron`).
- Для кожної сім'ї й кожного запланованого дня до вчорашнього (за місцевим часом) без запису створюється запис `missed`.
- Записи `pending` / `in_progress` за минулі дні переходять у `missed`. Частково виконаний день не оплачується.
- Функція ідемпотентна: повторний запуск нічого не ламає.

### 8.4 Серія та статистика

- **Серія (streak)** = кількість запланованих днів поспіль зі статусом `completed`, рахуючи від останнього завершеного або сьогоднішнього. Незаплановані дні серію **не переривають**. Якщо сьогоднішній день ще `pending`, він не перериває серію.
- **Completion rate** = `completed` / (`completed` + `missed`) за всі минулі дні.
- Функція `get_family_stats(family_id)` повертає: `earned_total`, `settled_total` (підтверджені переказами), `pending_total`, `owed`, `days_completed`, `completion_pct`, `current_streak`.

### 8.5 Розрахунки

Гроші в застосунку — це **облік**. Реальний переказ відбувається поза ним.

```
owed (належить) = сума earn − сума підтверджених settlement
pending          = сума settlement у статусі pending
```

Потік:

1. Дитина переказує гроші батьку/матері банком, BLIK тощо.
2. Дитина натискає **«Переказ зроблено»**, вводить суму. Створюється `settlement` зі статусом `pending`. Сума не може перевищувати `owed − pending`.
3. Батько/мати отримує push і бачить запис у «Історії».
4. Батько/мати натискає **«Так, отримано»** (`confirmed`) або **«Ні, не отримано»** (`rejected`).
5. Після підтвердження `owed` зменшується. Дитина отримує push.

Правило: підтвердити або відхилити може лише батько/мати. Дитина не може скасувати або змінити свій переказ у v1.

### 8.6 Відео

- Приватний bucket `exercise-videos`. Шлях: `{family_id}/{session_id}/{exercise_id}.mp4`.
- Завантаження: батько/мати своєї сім'ї (підписаний upload URL). Читання: обидва члени сім'ї (підписаний URL на 1 годину).
- `video_expires_at = completed_at + 7 днів`.
- Функція `purge-videos` (щодня, 03:00 UTC) видаляє файли зі Storage й виставляє `video_deleted_at`.
- Обмеження файлу: ≤ 30 МБ, `video/mp4` та `video/quicktime`.

### 8.7 Нагадування батькові (локальні)

- Плануються **локальні сповіщення** на пристрої батька/матері (`expo-notifications`), сервер не потрібен.
- Схема: на **найближчі 14 днів** створюються одноразові сповіщення на запланований час у кожен день плану.
- Перепланування: при запуску застосунку, при поверненні у foreground та після отримання оновленого плану (Realtime на рядок `families`).
- Після завершення сьогоднішнього дня: скасувати сьогоднішнє сповіщення.
- Обмеження v1: якщо дитина змінила план, а застосунок батька/матері не відкривався, старий розклад діє до наступного відкриття.
- Текст: «Час для вправ! {ім'я дитини} чекає 💚».

### 8.8 Часові пояси

- Усі мітки часу в БД зберігаються в UTC (`timestamptz`).
- «Сьогодні» для батька/матері визначається за його `timezone`. Дитина бачить ті самі дні.
- `timezone` оновлюється при кожному запуску (мандрівки, зміна поясу).

## 9. Push-сповіщення

Технологія: Expo Push Service (APNs / FCM під капотом). Токен зберігається в `profiles.push_token` після дозволу користувача.

### 9.1 Події

| # | Кому | Подія | Джерело | Текст (uk) |
|---|---|---|---|---|
| 1 | Батько/мати | Час вправ | Локально (8.7) | «Час для вправ! Андрій чекає 💚» |
| 2 | Дитина | День виконано | Сервер (webhook на `sessions`) | «Мама виконала сьогоднішні вправи 💪» |
| 3 | Батько/мати | Дитина натиснула «Нагадати» | Edge Function `send-reminder` | «Нагадування від Андрія: не забудь потренуватись 💪» |
| 4 | Батько/мати | Дитина створила переказ | Сервер (webhook на `ledger`) | «Переказ від Андрія: €30. Підтвердьте, коли отримаєте» |
| 5 | Дитина | Батько/мати розглянув переказ | Сервер (webhook на `ledger`) | «Отримання €30 підтверджено ✅» / «Переказ €30 не підтверджено» |

Події 4–5 не були в v2.0, але потрібні для потоку розрахунків.

### 9.2 Правила

- Текст формується мовою одержувача (`profiles.language`).
- Для події 2 форма дієслова залежить від зв'язку: `mom`, `grandma` → «виконала»; `dad`, `grandpa` → «виконав»; `other` → нейтрально: «Сьогоднішні вправи виконано: {ім'я} ✅».
- Кожен push має `data.screen` для переходу: подія 2 → дашборд; 3 → «Сьогодні»; 4 → «Історія».
- Дозвіл на сповіщення просимо не одразу, а на окремому екрані з поясненням «навіщо» (для батька/матері: після приєднання до сім'ї; для дитини: після створення плану).
- Якщо Expo Push повертає `DeviceNotRegistered`, токен очищається.
- Android: потрібні FCM-облікові дані в EAS. Виконати в тиждень 2 (до тестування push).

## 11. Мови

- Підтримуються: **українська (uk)**, **polski (pl)**, **English (en)**.
- Мова визначається за мовою пристрою; якщо вона не uk/pl/en, використовується `en`. Користувач може змінити в профілі.
- Тексти інтерфейсу: `src/i18n/{uk,pl,en}.json`. Вправи: у БД (JSON).
- **Множина**: використовувати плюралізацію i18next (`_one`, `_few`, `_many`, `_other`), бо «1 день / 2 дні / 5 днів» відрізняється в uk і pl.
- **Суми**: єдиний хелпер `formatMoney(amount, currency, locale)` на `Intl.NumberFormat`.
- **Рід дієслів**: для тексту про батька/матір передбачити варіанти за зв'язком (`_f`, `_m`, `_n`), див. 9.2.
- Наукові джерела залишаються англійською.
- Юридичні тексти (Умови, Політика конфіденційності) потрібні на трьох мовах.
- Польські та українські переклади генерує AI, а потім їх перевіряє носій мови (мінімум для польської).

## 12. Модель даних

PostgreSQL (Supabase). Міграції зберігаються в `supabase/migrations/`. Усі часові мітки — `timestamptz` (UTC). Нижче наведена стартова схема; AI-агент може її уточнювати, зберігаючи суть і обмеження.

### 12.1 Схема

```sql
-- Типи
create type user_role         as enum ('parent', 'child');
create type relationship_type as enum ('mom', 'dad', 'grandma', 'grandpa', 'other');
create type session_status    as enum ('pending', 'in_progress', 'completed', 'missed');
create type ledger_type       as enum ('earn', 'settlement');
create type ledger_status     as enum ('confirmed', 'pending', 'rejected');

-- Профілі (id = auth.users.id; порожній рядок створює тригер після входу)
create table profiles (
  id                  uuid primary key references auth.users(id) on delete cascade,
  phone               text not null,
  name                text,
  age                 int check (age between 16 and 120),
  role                user_role,                       -- ставиться один раз (тригер забороняє зміну)
  language            text not null default 'uk' check (language in ('uk','pl','en')),
  timezone            text not null default 'Europe/Warsaw',
  push_token          text,
  gdpr_consent_at     timestamptz,
  disclaimer_seen_at  timestamptz,
  created_at          timestamptz not null default now(),
  updated_at          timestamptz not null default now()
);

-- Сім'я: дитина + батько/мати
create table families (
  id                    uuid primary key default gen_random_uuid(),
  child_id              uuid not null references profiles(id) on delete cascade,
  parent_id             uuid not null unique references profiles(id) on delete cascade,
  relationship          relationship_type not null default 'mom',
  rate                  numeric(6,2) not null default 5.00 check (rate between 1 and 20),
  currency              text not null default 'EUR' check (currency in ('EUR','PLN')),
  plan_days             smallint[] not null default '{1,2,4,5}'   -- ISO: 1=Пн … 7=Нд
                        check (cardinality(plan_days) between 1 and 7
                               and plan_days <@ array[1,2,3,4,5,6,7]::smallint[]),
  reminder_time         time not null default '10:00',
  last_reminder_sent_at timestamptz,
  created_at            timestamptz not null default now()
);

-- Запрошення
create table invites (
  id            uuid primary key default gen_random_uuid(),
  child_id      uuid not null references profiles(id) on delete cascade,
  code          text not null unique,
  relationship  relationship_type not null,
  expires_at    timestamptz not null default now() + interval '7 days',
  used_by       uuid references profiles(id) on delete set null,
  used_at       timestamptz,
  created_at    timestamptz not null default now()
);

-- Вправи (довідник)
create table exercises (
  id               uuid primary key default gen_random_uuid(),
  slug             text not null unique,
  sort_order       int  not null,
  category         text not null,                  -- strength | cardio | balance | breathing
  name             jsonb not null,                 -- {"uk": "...", "pl": "...", "en": "..."}
  target_reps      int,
  target_seconds   int,
  record_max_sec   int not null default 30,
  demo_video_url   text,
  benefit          jsonb not null,
  source_title     text,
  source_url       text,
  is_active        boolean not null default true,
  check (target_reps is not null or target_seconds is not null)
);

-- День
create table sessions (
  id                uuid primary key default gen_random_uuid(),
  family_id         uuid not null references families(id) on delete cascade,
  date              date not null,                 -- локальна дата батька/матері
  status            session_status not null default 'pending',
  exercises_total   int not null,
  exercises_done    int not null default 0,
  rate              numeric(6,2) not null,         -- ставка на момент створення дня
  earned            numeric(6,2) not null default 0,
  completed_at      timestamptz,
  created_at        timestamptz not null default now(),
  unique (family_id, date)
);

-- Виконана вправа
create table exercise_records (
  id                 uuid primary key default gen_random_uuid(),
  session_id         uuid not null references sessions(id) on delete cascade,
  exercise_id        uuid not null references exercises(id),
  video_path         text,                         -- null = «без відео»
  video_expires_at   timestamptz,
  video_deleted_at   timestamptz,
  completed_at       timestamptz not null default now(),
  unique (session_id, exercise_id)
);

-- Облік грошей (єдине джерело правди для балансу)
create table ledger (
  id           uuid primary key default gen_random_uuid(),
  family_id    uuid not null references families(id) on delete cascade,
  type         ledger_type   not null,
  amount       numeric(8,2)  not null check (amount > 0),
  currency     text          not null,
  status       ledger_status not null,
  session_id   uuid references sessions(id) on delete cascade,   -- лише для earn
  created_by   uuid references profiles(id) on delete set null,
  created_at   timestamptz not null default now(),
  resolved_at  timestamptz,
  check (
    (type = 'earn' and session_id is not null and status = 'confirmed')
    or type = 'settlement'
  )
);
-- Один earn на день: гарантує ідемпотентність нарахування
create unique index ledger_one_earn_per_session on ledger(session_id) where type = 'earn';

create index on sessions(family_id, date desc);
create index on ledger(family_id, created_at desc);
create index on exercise_records(video_expires_at) where video_deleted_at is null;
```

## 13. Безпека та RLS

### 13.1 Правила доступу

| Таблиця | SELECT | Запис |
|---|---|---|
| `profiles` | Свій рядок + рядок другого члена сім'ї | `UPDATE` лише свого рядка (ім'я, мова, часовий пояс, токен, згода) |
| `families` | Члени сім'ї | Лише через RPC `update_plan`, `accept_invite` |
| `invites` | Дитина-власник | Лише через RPC |
| `exercises` | Усі авторизовані | Закрито (лише міграції/Studio) |
| `sessions` | Члени сім'ї | Лише через RPC |
| `exercise_records` | Члени сім'ї (через `sessions`) | Лише через RPC |
| `ledger` | Члени сім'ї | Лише через RPC |

Для всіх таблиць: `ENABLE ROW LEVEL SECURITY`, прямих політик `INSERT/UPDATE/DELETE` для клієнта немає (окрім `profiles`).

### 13.2 Storage

```sql
-- Приватний bucket exercise-videos
create policy "parent uploads to own family folder" on storage.objects
  for insert to authenticated
  with check (
    bucket_id = 'exercise-videos'
    and exists (select 1 from families f
                where f.parent_id = auth.uid()
                  and f.id::text = (storage.foldername(name))[1])
  );

create policy "family members read videos" on storage.objects
  for select to authenticated
  using (
    bucket_id = 'exercise-videos'
    and exists (select 1 from families f
                where auth.uid() in (f.child_id, f.parent_id)
                  and f.id::text = (storage.foldername(name))[1])
  );
-- Видалення файлів: лише service_role (Edge Function purge-videos)
-- Bucket exercise-demos: публічне читання, запис лише через Studio
```

### 13.3 Загальні вимоги безпеки

- Усі RPC — `SECURITY DEFINER` з `set search_path = public`. Кожна функція перевіряє `auth.uid()` і належність до сім'ї.
- `service_role` ключ ніколи не потрапляє в застосунок або репозиторій (`.env`, секрети EAS / Supabase).
- Шлях відео в `complete_exercise` перевіряється на відповідність `{family_id}/{session_id}/{exercise_id}.mp4`.
- Валідація на сервері: суми, діапазони ставки, дні плану, стан дня.
- HTTPS/TLS скрізь. Шифрування даних у спокої забезпечує Supabase.
- Ризик, прийнятний для пілоту: підбір коду запрошення (6 символів, одноразовий, 7 днів, потрібен підтверджений номер телефону).
- Номер телефону видно другому члену сім'ї; при необхідності винести в окрему таблицю.

## 14. Серверні функції

### 14.1 RPC (Postgres-функції)

| Функція | Хто | Що робить |
|---|---|---|
| `create_invite(relationship)` | Дитина | Знецінює попередні невикористані запрошення, генерує код, повертає `code`, `expires_at` |
| `accept_invite(code)` | Батько/мати без сім'ї | Перевіряє код (дійсний, не використаний), створює `families`, позначає запрошення використаним |
| `update_plan(family_id, days, rate, currency, reminder_time)` | Дитина | Валідує та оновлює план (діє з наступного дня) |
| `get_or_create_today(family_id)` | Батько/мати | Рахує локальну дату; якщо день не в плані — `rest_day: true`; інакше створює/повертає `session` та список вправ зі станом (`done` / `current` / `locked`) |
| `complete_exercise(session_id, exercise_id, video_path?)` | Батько/мати | Транзакційно: перевіряє належність, сьогоднішню дату, статус, чергу вправ, шлях відео; вставляє `exercise_records` (повтор — без помилки), оновлює лічильники, при останній вправі ставить `completed`, `earned = rate` і вставляє `ledger earn` |
| `create_settlement(family_id, amount)` | Дитина | Перевіряє `amount ≤ owed − pending`, вставляє `ledger settlement / pending` |
| `resolve_settlement(ledger_id, accept)` | Батько/мати | Лише для `pending`; ставить `confirmed` або `rejected` і `resolved_at` |
| `get_family_stats(family_id)` | Члени сім'ї | `earned_total`, `settled_total`, `pending_total`, `owed`, `days_completed`, `completion_pct`, `current_streak` |
| `close_past_days()` | `pg_cron` | Див. 8.3 |

Код `complete_exercise` і `create_settlement` покривається SQL-тестами (мінімум): повторний виклик не подвоює нарахування; сума переказу не перевищує борг; чужа сім'я недоступна.

### 14.2 Edge Functions

| Функція | Тригер | Що робить |
|---|---|---|
| `send-push` | Database Webhooks: `sessions` UPDATE (`status → completed`), `ledger` INSERT (`settlement`), `ledger` UPDATE (`pending → confirmed / rejected`) | Формує текст мовою одержувача та надсилає через Expo Push API; очищає недійсні токени |
| `send-reminder` | Виклик клієнта (JWT) | Перевіряє, що викликає дитина з цієї сім'ї; ліміт 1 раз на 2 години (`families.last_reminder_sent_at`); надсилає push |
| `purge-videos` | `pg_cron`, щодня 03:00 UTC | Видаляє з Storage файли, у яких `video_expires_at < now()`, і ставить `video_deleted_at` |
| `delete-account` | Виклик клієнта (JWT) | Видаляє відео сім'ї зі Storage, видаляє сім'ю та профіль (каскад), видаляє користувача з Auth |

### 14.3 Розклад (`pg_cron`)

```sql
select cron.schedule('close-past-days', '5 * * * *', $$ select close_past_days(); $$);
-- purge-videos: щодня 03:00 UTC, виклик Edge Function через pg_net (net.http_post)
```

## 15. GDPR, приватність, дисклеймер

### 15.1 Які дані збираються

Номер телефону, ім'я, вік (необов'язково), мова, часовий пояс, push-токен, відео вправ (7 днів), записи про виконання днів та розрахунки. Нічого іншого.

### 15.2 Принципи

- Мінімізація даних. Реклами, профілювання й сторонньої аналітики немає.
- Дані в ЄС (Supabase, Frankfurt). Передача по TLS, шифрування в спокої.
- Відео приватні, доступ лише членам сім'ї через короткострокові підписані URL. Автовидалення через 7 днів.
- Договори обробки даних (DPA) із процесорами: Supabase, Twilio, Expo (push), Sentry (якщо підключений).
- Політика конфіденційності й Умови використання мовами uk / pl / en. На пілоті допустимі прості сторінки за посиланнями із consent-екрана.
- Застосунок призначений для повнолітніх (18+).

### 15.3 Права користувача

| Право | Реалізація у v1 |
|---|---|
| Доступ і виправлення | Ім'я, мова в профілі |
| Видалення (ст. 17 GDPR) | «Видалити акаунт» у застосунку (15.4) |
| Експорт (ст. 20 GDPR) | За запитом на пошту, вручну. Автоматизація у v2 |

### 15.4 Видалення акаунта

Вимога і GDPR, і Apple (видалення має бути доступне в застосунку).

1. Профіль → «Видалити акаунт».
2. Попередження: «Буде видалено акаунт, сім'ю, історію, розрахунки та відео. Цю дію не можна скасувати». Для обох ролей.
3. Подвійне підтвердження.
4. Edge Function `delete-account` видаляє відео, дані сім'ї та користувача.
5. Друга сторона при наступному відкритті бачить: «Друга сторона видалила акаунт». Батько/мати повертається на екран очікування, дитина — на «Запросити».

- Показується в consent-екрані (обов'язкові чекбокси).
- Доступний у профілі обох ролей для повторного перегляду.
- Тексти: «Не є медичним пристроєм і не замінює консультацію лікаря».

## 17. UX-принципи для аудиторії 50+

Найважливіший принцип: **простота**. Батько/мати не повинні вчитися користуватися застосунком.

- Основний текст ≥ 18 pt, заголовки 24–32 pt, кнопки висотою ≥ 56 pt, зони натискання ≥ 48 pt.
- **Одна головна дія на екрані.** Ніяких прихованих жестів (свайпи не єдиний спосіб).
- Проста мова, без термінів. Помилки — людською мовою й з варіантом «що робити».
- Небезпечні дії (видалення, «без відео») завжди з підтвердженням.
- Емодзі допомагають упізнавати екрани (👵, 💪, 🌿), але не замінюють підписи.
- Повага до системного розміру шрифту (`allowFontScaling`).
- Кожен екран перевіряється **на реальному телефоні** з реальною людиною віку 50+ (мінімум на 2-му тижні).

5. **Гроші й нарахування рахуються тільки на сервері (Postgres-функції).** Клієнт нічого не додає до балансу.
6. Усі таблиці мають RLS. Прямих записів у `sessions`, `exercise_records`, `ledger`, `families` з клієнта немає, лише через RPC.
7. Жодних секретів у коді. `service_role` ключ тільки в Edge Functions.
8. Кожна RPC перевіряє `auth.uid()` та належність до сім'ї, а також валідує вхідні дані.

**Код**

9. TypeScript `strict`. Типи БД генерувати (`supabase gen types typescript`), не писати вручну.
10. Усі тексти через i18n, без захардкоджених рядків.
11. Стилі лише через дизайн-токени (розділ 17). Мінімальний розмір тексту й кнопок — з розділу 17.
12. Дати рахувати у часовому поясі батька/матері; у БД зберігати UTC.
13. Малі файли, один компонент — одна відповідальність. Серверні дані через TanStack Query.

**Перевірка**

14. Камеру, push та відео перевіряти **тільки на реальному пристрої**.
15. Для `complete_exercise`, `create_settlement`, `close_past_days` — SQL-тести (ідемпотентність, межі сум, чужа сім'я).
16. Перед завершенням фічі: перевірити чек-лист із розділу 18 і всі три мови.

## 21. Глосарій

| Термін | Значення |
|---|---|
| **Сім'я** | Пара «дитина + батько/мати» з власним планом, ставкою та балансом |
| **День (session)** | Запис про запланований день занять сім'ї |
| **Ставка** | Сума винагороди за повністю виконаний день (за замовчуванням €5) |
| **Належить (owed)** | Зароблено мінус підтверджені перекази |
| **Переказ (settlement)** | Запис про грошовий переказ від дитини, що потребує підтвердження батьком/матір'ю |
| **Серія (streak)** | Кількість запланованих днів поспіль зі статусом «виконано» |
| **Completion rate** | Частка виконаних днів від запланованих |
| **OTP** | Одноразовий код із SMS для входу |
| **RLS** | Row Level Security, правила доступу до рядків у Postgres |
| **RPC** | Функція в базі даних, яку викликає клієнт |
| **EAS** | Expo Application Services, хмарна збірка й оновлення |
| **Dev build** | Збірка застосунку зі своїми нативними модулями (на відміну від Expo Go) |
| **GDPR** | Загальний регламент ЄС про захист даних |

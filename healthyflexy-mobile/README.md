## 0. Про цей документ і що в ньому змінилось

Це не новий продуктовий задум, а **оновлення ТЗ v3.0 до фактичного стану коду**. Продуктова ідея, ролі, аудиторія 50+ і принципи спрощення (розділ 1) не змінились. Змінилися технічні рішення, прийняті під час розробки, і додано дві продуктові можливості, яких не було в v3.0. Нижче — коротко, що саме інакше; детально — у відповідних розділах.

**Технічні рішення, що відрізняються від v3.0:**

1. **Бекенд — не Supabase, а власний сервер.** NestJS + TypeORM + PostgreSQL, розгорнутий на Railway (а не Supabase-проєкт). Причина: потрібен більший контроль над бізнес-логікою нарахувань, діагностикою запуску та форматом помилок, ніж дає комбінація RLS-політик і Postgres-функцій.
2. **Фото замість відео.** Замість запису відеоролика під час вправи застосунок робить **3 фотокадри**. Це простіше для аудиторії 50+ (не треба розуміти «запис/стоп»), менше важить, швидше завантажується на слабкому інтернеті. Логіка довіри та автовидалення через 7 днів лишилися такими ж, як планувались для відео.
3. **Вхід телефоном ЧИ поштою.** У v3.0 був лише SMS-код. Додано альтернативний вхід через код на електронну пошту (Resend), бо SMS-провайдер коштує грошей навіть на тестуванні, а частина тестерів не готова платити за пілот. Обидва канали рівноправні: акаунт належить або номеру, або пошті.
4. **Четверта мова — російська.** До української, польської, англійської додана російська (тексти інтерфейсу перекладені повністю; вправи на сервері поки повертаються українською для `ru`, оскільки основна аудиторія пілоту з цим змирилась).
5. **Сховище кадрів — змінне.** Не прив'язане до одного постачальника: `StorageProvider` абстракція з двома реалізаціями — локальний диск (для Railway з Volume) або S3-сумісне сховище (S3/R2). Дозволяє почати без витрат на S3.
6. **Дизайн переписано.** Емодзі-іконки замінені на векторні (`lucide-react-native`), додані плавні анімації появи елементів і власні SVG-ілюстрації. Емодзі свідомо лишені лише для аватарів членів сім'ї та вибору ролі — це відповідає принципу «емодзі впізнавані, але не замінюють підписи» з розділу 17, просто звужено їх застосування.
7. **Вхід лише з кодом підтвердження** (лист або SMS): тестових акаунтів і входу без коду немає; вкладка «Телефон» показується, лише якщо на сервері налаштовано SMS.

**Що НЕ змінилось:** зміст вправ (ті самі 4), правила нарахування й розрахунків (розділ 8), принципи UX для 50+ (розділ 17, крім деталей дизайн-токенів), права GDPR і видалення акаунта (розділ 15), критерії успіху пілоту (розділ 1.4).

Документ, як і раніше, можна класти в репозиторій і давати AI-агенту як джерело правди; правила для агента оновлені в розділі 19.

## 1. Продукт і мета MVP

### 1.1 Опис

Healthyflexy («Книжка турботи») — сімейний мобільний застосунок. Дорослі діти платять батькам 50+ грошову винагороду за щоденне виконання коротких фізичних вправ. Батько/мати виконує 4 вправи (≈10–15 хв) і робить кілька фотокадрів кожної. Після виконання всіх вправ дня система автоматично нараховує винагороду. Дитина бачить прогрес у реальному часі, переглядає кадри та рахується з батьком/матір'ю.

### 1.2 Основна гіпотеза

Грошова винагорода від близької людини — найсильніший мотиватор для формування щоденної звички у людей 50+. Це не абонемент і не нагадування, а сімейний договір із фінансовим зобов'язанням.

### 1.3 Мета пілоту

- 5–20 реальних сімей.
- 2–3 тижні використання.
- Збір якісного фідбеку (інтерв'ю з батьками й дітьми).

### 1.4 Критерії успіху пілоту

Усі метрики рахуються SQL-запитами по базі, окремої аналітики немає.

| Метрика | Ціль |
|---|---|
| Completion rate (виконані дні / заплановані дні) | ≥ 70% |
| Середня поточна серія (streak) по сім'ях | ≥ 7 днів |
| Сім'ї, де хоча б один переказ підтверджений батьком | ≥ 60% |
| Якісний фідбек | Мінімум 5 інтерв'ю |

## 2. Обсяг v1

### 2.1 Входить у v1

- Згода (consent), медичний дисклеймер, онбординг.
- Вхід по номеру телефону (SMS-код) АБО електронній пошті (код у листі).
- Дві ролі: батько/мати та дитина.
- Зв'язок акаунтів через код або посилання-запрошення.
- Щоденні 4 вправи: демо, 3 фотокадри, автоматичне нарахування за день.
- Дашборд дитини: статус, баланс, фотокадри, «Нагадати».
- План: дні тижня, ставка, час нагадування.
- Облік розрахунків: «Переказ зроблено» / «Підтверджено».

- Push-сповіщення.
- Чотири мови: українська, російська, польська, англійська.

### 3.2 Схема

```
┌──────────────────────┐        ┌───────────────────────────────────┐
│  Expo app (iOS/And.) │◄──────►│  NestJS API (Railway)              │
│  Expo Router         │  HTTPS │  • Auth (JWT + SMS/email OTP)      │
│  TanStack Query      │  WS    │  • Users / Families / Invites      │
│  expo-camera         │        │  • Exercises / Workouts / Ledger   │
│  expo-notifications  │        │  • Notifications (push + realtime) │
└──────────┬───────────┘        │  • Storage (photo URLs)            │
           │                    │  • Scheduler (@nestjs/schedule)    │
           │ push               └───────────┬─────────┬─────────────┘
           ▼                                │         │

                                     (Railway)      (SMS / email)
```

### 3.3 Архітектурні принципи

1. **Вся бізнес-логіка з грошима та нарахуваннями — тільки на сервері**, у транзакційних методах сервісів NestJS (`WorkoutsService`, `LedgerService`). Клієнт ніколи не рахує й не записує баланс.
2. **Доступ до даних перевіряється в кожному ендпоінті**, а не декларативними політиками бази: guard перевіряє JWT і роль, сервіс окремо перевіряє належність запису до сім'ї того, хто робить запит (`requireFamilyFor`).
3. **У застосунку немає жодних серверних секретів.** Ключі Twilio, Resend, підпису сховища й JWT живуть лише у змінних середовища бекенду.
4. **Один клієнт — один екран — один запит.** TanStack Query для серверних даних, невеликі локальні стори для стану UI й сесії.
5. **Потрібен інтернет.** Offline-режиму у v1 немає.
6. **Усі тексти через i18n.** Жодних захардкоджених рядків у компонентах.
7. **Сервер сам себе діагностує.** При кожному старті `StartupDiagnostics` перевіряє підключення до бази, застосування міграцій, права запису в сховище, коректність `PUBLIC_BASE_URL`, наявність провайдерів SMS/пошти — і друкує в лог і ✅, і ❌ з підказкою, що виправити.

### 3.5 Середовища

- Один бекенд-сервіс на Railway на пілоті (окремих dev/prod проєктів поки нема — розділяються змінними середовища й гілками).
- Міграції застосовуються автоматично при кожному старті сервера (ідемпотентно), окрім тестового оточення.
- Postgres-Volume на Railway для локального сховища фото, щоб кадри не зникали при кожному деплої.
- Типи запитів/відповідей спільні за домовленістю (ручна синхронізація DTO бекенду й типів мобільного застосунку), автогенерації типів з бекенду поки немає.

## 4. Ролі користувачів

### 4.1 Батько/мати (parent), основний користувач

Людина 50–80 років, живе окремо від дітей, низький технічний рівень. Головна цінність: простота й відчуття турботи, а не контролю.

- Бачить сьогоднішні вправи в максимально простому вигляді.
- Виконує вправу за демонстрацією та фотографує себе на камеру (3 кадри).
- Отримує автоматичне нарахування за виконаний день.
- Бачить баланс, серію, календар та історію розрахунків.
- Підтверджує отримання переказу від дитини.

### 4.2 Дитина (child), спонсор

Дорослий 30–55 років. Головна цінність: бачити, що батько/мати активні та здорові, без надокучливого контролю.

- Створює акаунт і запрошує батька/матір.
- Налаштовує план: дні, ставка, час нагадування.
- Бачить статус дня та переглядає фотокадри.
- Надсилає нагадування.
- Фіксує переказ грошей («Переказ зроблено»).

### 4.3 Адміністратор

Окремої ролі й інтерфейсу немає. Команда працює через Supabase Studio та SQL.

### 4.4 Правила зв'язку

- Одна дитина ↔ один батько/мати в інтерфейсі v1. Схема БД дозволяє розширення: `parent_id` унікальний, `child_id` — ні.
- Один батько/мати може бути в одній сім'ї.
- Роль обирається один раз і не змінюється (тригер у БД це забороняє).
- Застосунок призначений для повнолітніх (18+).

## 5. Онбординг та автентифікація

### 5.1 Порядок першого запуску

`Згода → Онбординг (3 слайди) → Телефон або пошта → код підтвердження → Роль → Ім'я → (батько: чекає запрошення / дитина: перший план + запрошення)`

Згода й онбординг показуються один раз. Стан зберігається локально, а після реєстрації згода записується в профіль користувача.

### 5.2 Екран згоди (Consent)

Без змін відносно v3.0: обов'язковий, показується один раз, три обов'язкові чекбокси (не медична рекомендація; згода з умовами й політикою; консультація з лікарем), кнопка активна лише коли відмічені всі три.

### 5.3 Онбординг (3 слайди)

Без змін по суті. Ілюстрації слайдів тепер власні SVG-компоненти (`WelcomeIllustration`, `ExerciseIllustration`, `RewardIllustration`), а не емодзі, з легким паралаксом при гортанні.

### 5.4 Реєстрація та вхід — телефон або пошта

На відміну від v3.0, де був лише один спосіб, тепер на екрані входу вгорі є перемикач: **«📱 Телефон»** і **«✉️ Пошта»**. Перемикання не перезавантажує екран — це один компонент з анімованим повзунком, під ним просто змінюється поле вводу. Обидва шляхи рівноправні й ведуть до того самого кроку підтвердження коду.

| Крок | Телефон | Пошта |
|---|---|---|
| 1 | Номер, вибір країни (за замовчуванням Польща 🇵🇱, є Україна 🇺🇦) | Адреса електронної пошти |
| 1а | Велике підтвердження «Цей номер правильний?» | Велике підтвердження «Ця адреса правильна?» |
| 2 | 6-значний код із SMS | 6-значний код із листа |
| 3 | Вибір ролі: **«Я батько/мати»** / **«Я дитина»** (спільний для обох каналів) | те саме |
| 4а/4б | Ім'я (для батька/матері — вік необов'язково) | те саме |
| 5а/5б | Батько/мати: «Чекаємо на запрошення» / Дитина: перший план + запрошення | те саме |

Акаунт належить **або** номеру телефону, **або** адресі пошти — не обом одразу. Це два незалежні шляхи входу, а не два способи підтвердити один акаунт.

**Технічні деталі коду підтвердження (спільні для обох каналів):**

- Код: 6 цифр, діє 5 хвилин, повторний запит можливий через 60 секунд, після 5 невірних спроб код анулюється.
- У базі зберігається лише HMAC-хеш коду, не сам код.
- Тестових номерів і адрес із фіксованим кодом немає: код завжди випадковий і приходить лише листом/SMS. Правильний код із листа = пошту підтверджено.
- SMS: Twilio, обмежений дозволеними країнами (`SMS_ALLOWED_COUNTRIES`, за замовчуванням Польща й Україна) — захист від випадкових витрат і SMS-шахрайства.
- Пошта: Resend зі свого підтвердженого домену (`MAIL_FROM=auth@<домен>`, SPF/DKIM у DNS), брендований лист із кодом мовою користувача.
- Після входу зберігаються мова пристрою (якщо це uk/ru/pl/en, інакше en) і часовий пояс (IANA, з пристрою).

### 5.5 Зв'язок акаунтів (запрошення)

Без змін відносно v3.0: 6-символьний код без символів, що плутаються (`0 O 1 I L`), діє 7 днів, одноразовий, нова пропозиція знецінює попередню. Дитина ділиться кодом через системне меню «Поділитися». Universal Links (https-посилання, що напряму відкриває застосунок) — як і раніше відкладено до v2, основний шлях — введення коду вручну.

## 8. Бізнес-логіка

### 8.1 День (сесія)

- «День» — це окремий запис: одна сім'я, одна дата.
- Дата рахується **за часовим поясом батька/матері**.
- Запис створюється при першому відкритті екрана «Сьогодні» — лише якщо день входить у план занять.
- У записі фіксуються: кількість активних вправ і ставка на момент створення дня (зміна ставки пізніше не зачіпає вже створені дні).
- Статуси: очікує → у процесі → виконано або пропущено.

### 8.2 Нарахування

1. Кожна вправа фіксується транзакційним методом на сервері (`WorkoutsService`). Він перевіряє, що вправа наступна в черзі та що день сьогоднішній і не завершений.
2. Коли виконано всі вправи дня, день стає завершеним, нараховується повна ставка, у журналі розрахунків створюється один запис нарахування (захищено від дублювання: повторний виклик для того самого дня безпечний).
3. Часткове виконання **не оплачується**.
4. Вправа без фото («Зарахувати без фото») зараховується так само, але дитина бачить позначку «без фото».

### 8.3 Пропущені дні

- Фонова задача (`@nestjs/schedule`) запускається щогодини.
- Для кожної сім'ї й кожного запланованого дня до вчорашнього (за місцевим часом) без запису створюється запис «пропущено».
- Незавершені записи за минулі дні переходять у «пропущено». Частково виконаний день не оплачується.
- Задача ідемпотентна: повторний запуск нічого не ламає.

### 8.4 Серія та статистика

- **Серія (streak)** = кількість запланованих днів поспіль зі статусом `completed`, рахуючи від останнього завершеного або сьогоднішнього. Незаплановані дні серію **не переривають**. Якщо сьогоднішній день ще `pending`, він не перериває серію.
- **Completion rate** = `completed` / (`completed` + `missed`) за всі минулі дні.
- Окремий запит статистики сім'ї повертає: `earned_total`, `settled_total` (підтверджені переказами), `pending_total`, `owed`, `days_completed`, `completion_pct`, `current_streak`.

### 8.5 Розрахунки

Гроші в застосунку — це **облік**. Реальний переказ відбувається поза ним.

```
owed (належить) = сума earn − сума підтверджених settlement
pending          = сума settlement у статусі pending
```

Потік:

1. Дитина переказує гроші батьку/матері банком, BLIK тощо.
2. Дитина натискає **«Переказ зроблено»**, вводить суму. Створюється `settlement` зі статусом `pending`. Сума не може перевищувати `owed − pending`.
3. Батько/мати отримує push і бачить запис у «Історії».
4. Батько/мати натискає **«Так, отримано»** (`confirmed`) або **«Ні, не отримано»** (`rejected`).
5. Після підтвердження `owed` зменшується. Дитина отримує push.

Правило: підтвердити або відхилити може лише батько/мати. Дитина не може скасувати або змінити свій переказ у v1.

### 8.6 Фотокадри

- Приватне сховище (локальний диск або S3/R2 — залежно від налаштування). Ключ кадру: `{familyId}/{sessionId}/{exerciseId}/{1..3}.jpg`.
- Завантаження: батько/мати своєї сім'ї, через підписаний URL для кожного з 3 кадрів окремо. Читання: обидва члени сім'ї (підписаний URL діє 1 годину).
- Термін життя кадру: 7 днів від моменту виконання вправи.
- Щоденна фонова задача видаляє файли зі сховища й позначає їх видаленими в базі.
- Обмеження файлу: JPEG, до 1 МБ на кадр.

### 8.7 Нагадування батькові (локальні)

- Плануються **локальні сповіщення** на пристрої батька/матері (`expo-notifications`), сервер не потрібен.
- Схема: на **найближчі 14 днів** створюються одноразові сповіщення на запланований час у кожен день плану.
- Перепланування: при запуску застосунку, при поверненні у foreground та після отримання оновленого плану (Realtime на рядок `families`).
- Після завершення сьогоднішнього дня: скасувати сьогоднішнє сповіщення.
- Обмеження v1: якщо дитина змінила план, а застосунок батька/матері не відкривався, старий розклад діє до наступного відкриття.
- Текст: «Час для вправ! {ім'я дитини} чекає 💚».

### 8.8 Часові пояси

- Усі мітки часу в БД зберігаються в UTC (`timestamptz`).
- «Сьогодні» для батька/матері визначається за його `timezone`. Дитина бачить ті самі дні.
- `timezone` оновлюється при кожному запуску (мандрівки, зміна поясу).

| 4 | Батько/мати | Дитина створила переказ | Сервер, модуль Notifications | «Переказ від Андрія: {сума}. Підтвердьте, коли отримаєте» |
| 5 | Дитина | Батько/мати розглянув переказ | Сервер, модуль Notifications | «Отримання {сума} підтверджено» / «Переказ {сума} не підтверджено» |

Події 4–5 не були в v2.0, але потрібні для потоку розрахунків. Емодзі в текстах push-повідомлень тепер не використовуються (узгоджено з рештою дизайну).

### 9.2 Правила

- Текст формується мовою одержувача (`profiles.language`).
- Для події 2 форма дієслова залежить від зв'язку: `mom`, `grandma` → «виконала»; `dad`, `grandpa` → «виконав»; `other` → нейтрально: «Сьогоднішні вправи виконано: {ім'я} ✅».
- Кожен push має `data.screen` для переходу: подія 2 → дашборд; 3 → «Сьогодні»; 4 → «Історія».
- Дозвіл на сповіщення просимо не одразу, а на окремому екрані з поясненням «навіщо» (для батька/матері: після приєднання до сім'ї; для дитини: після створення плану).
- Якщо Expo Push повертає `DeviceNotRegistered`, токен очищається.
- Android: потрібні FCM-облікові дані в EAS. Виконати в тиждень 2 (до тестування push).

## 11. Мови

- Підтримуються: **українська (uk)**, **русский (ru)**, **polski (pl)**, **English (en)**.
- Мова визначається за мовою пристрою; якщо вона не uk/ru/pl/en, використовується `en`. Користувач може змінити в профілі (сітка 2×2 з назвами рідною мовою).
- Тексти інтерфейсу: `src/i18n/locales/{uk,ru,pl,en}.json`, кожен файл перекладений повністю й окремо (жоден не є копією іншого). Вправи: у базі бекенду (поле з перекладами на кожну мову).
- **Особливість `ru`:** бекенд поки не має окремого поля мови `ru` для назв і текстів вправ — для російського інтерфейсу назви й тексти вправ мапляться на українські на сервері, а мобільний застосунок підміняє їх заздалегідь підготованими російськими текстами на клієнті. Мова, яку сервер зберігає в профілі (для листів, SMS, push), для `ru`-користувача — `uk`. Це тимчасове рішення, задокументоване в коді; коли бекенд отримає власне значення `ru`, підміну можна прибрати.
- **Множина**: використовується плюралізація i18next (`_one`, `_few`, `_many`, `_other`) — форми відрізняються в uk, ru і pl.
- **Суми**: єдиний хелпер форматування через `Intl.NumberFormat`.
- **Рід дієслів**: для тексту про батька/матір передбачені варіанти за зв'язком (мама/бабуся → жіночий рід, тато/дідусь → чоловічий, інше → нейтрально).
- Наукові джерела залишаються англійською.
- Юридичні тексти (Умови, Політика конфіденційності) потрібні на чотирьох мовах.
- Переклади генерує AI, а потім їх перевіряє носій мови (мінімум для польської та російської).

## 12. Модель даних

PostgreSQL, схема керується версійними міграціями TypeORM (не Supabase). Усі часові мітки зберігаються в UTC. Нижче — спрощений опис сутностей і зв'язків: точні назви колонок, типи й індекси — у файлах міграцій репозиторію бекенду, тут наведена суть, якої агент і розробники мають дотримуватись.

### 12.1 Сутності

**Користувач (`users`)**
Один рядок на людину, незалежно від ролі. Вхід прив'язаний **або** до номера телефону, **або** до адреси пошти — рівно одне з двох заповнене (перевіряється обмеженням на рівні бази). Зберігає: ім'я, вік (необов'язково, лише для батька/матері), роль (`parent` / `child`, встановлюється один раз і після цього незмінна), мову інтерфейсу, часовий пояс, налаштування push, часові мітки згоди й перегляду дисклеймера.

**Код підтвердження (`otp_codes`)**
Одна ціль (`target`) — номер телефону або адреса пошти, HMAC-хеш коду (сам код не зберігається), час дії, скільки невірних спроб було, чи використаний.

**Сім'я (`families`)**
Пара «дитина + батько/мати»: одна дитина може мати кілька записів сімей лише теоретично (модель це дозволяє), але поточний застосунок працює з одним активним зв'язком, як і в v3.0. Зберігає: тип родинного зв'язку (мама/тато/бабуся/дідусь/інше), ставку, валюту (EUR/PLN), дні плану занять (масив днів тижня), час нагадування батькові.

**Запрошення (`invites`)**
6-символьний код, кому належить (дитина), тип родинного зв'язку, термін дії (7 днів), ким і коли використаний.

**Вправа (`exercises`)** — довідник, керується лише сідером/міграціями, клієнт його не змінює. Порядок у дні, категорія, назва й текст «Користь» на кожну мову, ціль (повторення або секунди), необов'язкове демо-відео, джерело.

**Сесія дня (день занять)**
Один запис на сім'ю на календарну дату (за часовим поясом батька/матері). Статус (очікує / у процесі / виконано / пропущено), скільки вправ виконано з скількох, ставка, зафіксована на момент створення дня, скільки нараховано.

**Запис виконання вправи**
Прив'язаний до сесії дня й конкретної вправи. Замість шляху до відео (як у v3.0) зберігає до 3 ключів фотокадрів у сховищі, час завершення, час, коли фото стають недоступними (+7 днів), і чи вже видалені фактично.

**Журнал розрахунків (`ledger`)**
Єдине джерело правди для балансу. Два типи записів: нарахування за виконаний день (створюється автоматично, один на день) і переказ (створює дитина, підтверджує або відхиляє батько/мати). Статуси переказу: очікує / підтверджено / відхилено.

### 12.2 Обчислювані величини (без окремих таблиць)

- **Належить (owed)** = сума нарахувань − сума підтверджених переказів.
- **Очікує (pending)** = сума переказів у статусі «очікує підтвердження».
- **Серія (streak)** = кількість запланованих днів поспіль зі статусом «виконано», рахуючи від останнього завершеного або сьогоднішнього; незаплановані дні серію не переривають.
- **Completion rate** = виконані дні / (виконані + пропущені) за весь час.

Ці величини рахуються запитом до бази на льоту (агрегація по `ledger` і сесіях), окремого кешу чи матеріалізованого подання поки немає — навантаження пілоту (до ~100 користувачів) цього не потребує.

### 12.3 Початкові дані

Сідер бекенду створює 4 вправи з розділу 10.2 (назви й тексти на чотирьох мовах — для `ru` тексти вправ на сервері поки збігаються з `uk`, див. розділ 11) при першому старті, якщо довідник порожній.

## 13. Безпека

У v3.0 доступ до даних описувався декларативними RLS-політиками й Postgres-функціями Supabase. У фактичній реалізації бекенд свій, тому та сама модель безпеки реалізована інакше — по суті так само суворо, але засобами NestJS.

### 13.1 Як перевіряється доступ

- Кожен запит, крім явно позначених `@Public()` (вхід, реєстрація, перевірка коду), проходить через **guard**, який перевіряє дійсний JWT access-токен.
- Access-токен живе недовго; оновлення — через refresh-токен з ротацією (використаний refresh-токен одразу стає недійсним).
- Кожен сервісний метод, що працює з даними сім'ї (дні, вправи, розрахунки, план), окремо перевіряє, що користувач, який робить запит, дійсно належить до цієї сім'ї (`requireFamilyFor` та подібні перевірки) — це заміна RLS-політик Supabase, перевірка робиться в коді, а не в базі.
- Роль користувача (`parent`/`child`) перевіряється там, де дія дозволена лише одній стороні (наприклад, підтвердити переказ може лише батько/мати, створити переказ — лише дитина).
- Довідник вправ і будь-які «глобальні» дані клієнт змінювати не може — лише сідер і міграції.

### 13.2 Сховище фото

- Кадри приватні: підписаний URL (HMAC, з терміном дії) видається лише члену тієї самої сім'ї, до якої належить кадр.
- Завантажувати нові кадри може лише батько/мати своєї сім'ї, і лише для сесії дня, яка ще не завершена.
- Видалення файлів через 7 днів виконує лише фонова задача сервера, у клієнта такого доступу немає.

### 13.3 Загальні вимоги безпеки

- Жодних секретів у мобільному застосунку чи в репозиторії: ключі JWT, підпису сховища, Twilio, Resend і адреса бази — лише у змінних середовища бекенду.
- Валідація вхідних даних на сервері для кожного ендпоінту (DTO з декораторами `class-validator`): суми, діапазони ставки, дні плану, формат номера й пошти, довжина коду.
- HTTPS/TLS на з'єднанні з Railway.
- Ризик, прийнятний для пілоту: підбір коду запрошення (6 символів, одноразовий, діє 7 днів).
- Тимчасовий режим входу без коду (розділ 5.6) — свідомо прийнятий і задокументований ризик лише для закритого тестування, з обмеженням за списком номерів і голосним попередженням у логах, поки увімкнений.
- Номер телефону чи адреса пошти видно другому члену сім'ї (потрібно для розуміння, з ким саме зв'язана сім'я) — як і в v3.0.

## 14. Серверні модулі й фонові задачі

У v3.0 серверна логіка описувалась як набір Postgres RPC-функцій і Supabase Edge Functions. У реалізації це модулі NestJS — по суті ті самі дії, інша форма.

### 14.1 Модулі (замість RPC)

| Модуль | Хто звертається | Що робить |
|---|---|---|
| `Auth` | Усі | Вхід за SMS-кодом, вхід за кодом з пошти, тимчасовий вхід без коду (5.6), видача й оновлення JWT, вихід (в тому числі «на всіх пристроях») |
| `Users` | Усі | Профіль, вибір ролі (один раз), мова, часовий пояс, налаштування push, видалення акаунта |
| `Invites` | Дитина створює, батько/мати приймає | Генерація й перевірка коду запрошення, знецінення попередніх |
| `Families` | Обидва | План (дні, ставка, валюта, час нагадування), дані про зв'язок |
| `Exercises` | Обидва (читання) | Довідник вправ, локалізовані тексти |
| `Workouts` | Обидва | «Сьогодні» (створення/повернення дня), URL для завантаження кадрів, транзакційне зарахування вправи, закриття прострочених днів |
| `Ledger` | Обидва | Нарахування (автоматично), створення переказу (дитина), підтвердження/відхилення (батько/мати), статистика сім'ї |
| `Notifications` | Сервер → клієнт | Push-повідомлення (події з таблиці 9.1), realtime-оновлення статусу дня через WebSocket |
| `Storage` | Внутрішньо | Абстракція над сховищем кадрів: підписані URL, вибір локального диска чи S3/R2 |
| `Sms` / `Email` | Внутрішньо (через `Auth`) | Надсилання коду підтвердження; кожен має провайдера для продакшену (Twilio / Resend) і консольного для розробки |
| `Audit` | Внутрішньо | Журнал важливих подій (вхід без коду, видалення акаунта тощо) |
| `Health` | Інфраструктура | `/health` для перевірки живості сервісу (Railway healthcheck) |

Код зарахування вправи й створення переказу покритий e2e-тестами (мінімум): повторний виклик не подвоює нарахування; сума переказу не перевищує борг; чужа сім'я недоступна.

### 14.2 Фонові задачі (замість `pg_cron` і Edge Functions на розкладі)

| Задача | Розклад | Що робить |
|---|---|---|
| Закриття прострочених днів | щогодини | Див. 8.3 |
| Видалення старих кадрів | щодня | Видаляє зі сховища кадри старші 7 днів, позначає їх видаленими в базі |

Обидві реалізовані через `@nestjs/schedule` у самому процесі бекенду — окремого воркера чи черги задач немає (не потрібно для навантаження пілоту).

### 14.3 Діагностика при старті

Кожен запуск сервера друкує в лог блок стану: підключення до бази, чи застосовані всі міграції, скільки вправ у довіднику, чи налаштовані SMS/пошта і яким провайдером, чи є права запису в сховище кадрів, коректність публічної адреси сервера. Проблеми позначені ❌ (блокує роботу функції) або ⚠️ (працює, але варто виправити) з готовою підказкою, що зробити — це замінює частину роботи, яку в Supabase-варіанті виконував би Studio/дашборд.

## 15. GDPR, приватність, дисклеймер

### 15.1 Які дані збираються

Номер телефону АБО адреса пошти (не обидва), ім'я, вік (необов'язково), мова, часовий пояс, push-токен, фотокадри вправ (7 днів), записи про виконання днів та розрахунки. Нічого іншого.

### 15.2 Принципи

- Мінімізація даних. Реклами, профілювання й сторонньої аналітики немає.
- Дані на сервері в Railway (регіон вказується при налаштуванні проєкту). Передача по TLS.
- Фотокадри приватні, доступ лише членам сім'ї через короткострокові підписані URL. Автовидалення через 7 днів.
- Договори обробки даних (DPA) із процесорами: Railway, Twilio (SMS), Resend (пошта), Expo (push).
- Політика конфіденційності й Умови використання мовами uk / pl / en. На пілоті допустимі прості сторінки за посиланнями із consent-екрана.
- Застосунок призначений для повнолітніх (18+).

## 17. UX-принципи та дизайн-система

Найважливіший принцип не змінився: **простота** для аудиторії 50+. Батько/мати не повинні вчитися користуватися застосунком.

### 17.1 Принципи (без змін по суті)

- Основний текст ≥ 15 pt (типографіка масштабована, з опорою на системний розмір шрифту), заголовки помітно більші, кнопки висотою ≥ 52 pt, зони натискання ≥ 44 pt.
- **Одна головна дія на екрані.** Ніяких прихованих жестів.
- Проста мова, без термінів. Помилки — людською мовою й з варіантом «що робити».
- Небезпечні дії (видалення акаунта, «зарахувати без фото») завжди з підтвердженням.
- Повага до системного розміру шрифту.

### 17.2 Іконки й емодзі — що змінилось

У v3.0 планувались емодзі як основний спосіб позначення екранів і дій. У фактичному дизайні це звужено:

- **Векторні іконки** (`lucide-react-native`, єдиний реєстр іменованих іконок у коді) — для всіх дій, категорій вправ, станів, навігації, повідомлень про помилки.
- **Емодзі лишені навмисно лише для:** аватарів членів сім'ї (мама/тато/бабуся/дідусь/інше — 👵 👴 🧑) і вибору ролі на екрані реєстрації. Це відповідає початковому принципу «емодзі впізнавані», просто застосовується вужче, а не як основна іконографія.
- **Власні SVG-ілюстрації** замість емодзі чи фотографій для: онбордингу, порожніх станів (немає фото, немає записів), дня відпочинку, святкування виконаного дня, очікування запрошення, помилки камери.

### 17.3 Рух і анімації (нове відносно v3.0)

У v3.0 про анімації не йшлося. У реалізації додано послідовну, помірну плавність:

- Картки й секції на кожному екрані з'являються невеликим каскадом (кожна наступна — з невеликою затримкою), а не всі одразу.
- Перемикачі (валюта, мова, дні тижня, спосіб входу телефон/пошта) анімовано підсвічують обраний варіант, а не миттєво перемальовуються.
- Кільце прогресу вправ і смуги прогресу заповнюються плавно, а не стрибком.
- Дрібні деталі: пружинна поява галочки при виконанні, легке «стиснення» кнопки при натисканні з тактильним відгуком.
- Правило: анімується лише прозорість і зсув/масштаб елементів, ніколи властивості, що змінюють розкладку сторінки під час самої анімації — це усуває «стрибки» інтерфейсу.

## 18. Стан реалізації відносно плану v3.0

У v3.0 було заплановано 3 тижні по тижнях. Розробка фактично не тримала жорстких тижневих меж (задачі йшли ітераціями, зокрема додавання пошти й повний редизайн — це вже не було в початковому 3-тижневому плані). Нижче — чесний стан за пунктами первинного плану, а не новий календарний план.

### Зроблено

- Проєкт Expo, структура застосунку та навігація (таби батька/дитини).
- Бекенд: NestJS-сервер з усіма модулями з розділу 14.1, розгорнутий на Railway з PostgreSQL і Volume для сховища кадрів.
- Автоматичні міграції бази при кожному старті сервера (ідемпотентні).
- Вхід: SMS-код (Twilio для продакшену, консольний провайдер для розробки), код на пошту (Resend для продакшену, консольний провайдер для розробки), тимчасовий вхід без коду для закритого тестування.
- Consent, онбординг, вибір ролі, ім'я — усі три мови v3.0 плюс російська.
- Запрошення: генерація й прийняття коду, deep link, екран очікування.
- Екран «Сьогодні»: створення/повернення дня, кільце прогресу, список вправ у черзі.
- Потік вправи: демо → 3 фотокадри → завантаження в сховище → нарахування.
- Нарахування дня, журнал розрахунків, статистика сім'ї, серія днів.
- Дашборд дитини з фотокадрами за тиждень, «Нагадати», журналом розрахунків.
- Екран «План» (дні, ставка, валюта, час нагадування).
- Розрахунки: «Переказ зроблено» → «Так, отримано» / «Ні, не отримано».
- Локальні нагадування батькові на пристрої.
- Щогодинне закриття прострочених днів, щоденне видалення старих кадрів.
- Історія: календар місяця, картки статистики, журнал розрахунків.
- Профілі обох ролей: мова (4 варіанти), сповіщення, дисклеймер, вихід (у тому числі «на всіх пристроях»), видалення акаунта.
- Повний редизайн: векторні іконки, анімації появи елементів, власні SVG-ілюстрації, узгоджена дизайн-система (розділ 17).
- Startup-діагностика сервера з підказками, що виправити.

### Відомі обмеження й не перевірено наживо

- **Push на Android (FCM)** і **push на iOS (APNs)** налаштовані на рівні коду (`expo-notifications`), але реальна доставка push на живих пристроях із production-обліковими даними ще не підтверджена в цьому циклі розробки.
- **Resend без власного домену**: реальні листи з кодом ідуть лише на адресу власника акаунта Resend. Для будь-яких інших користувачів потрібен підтверджений домен (SPF/DKIM) — це відкладено до появи домену.
- **Тестування з реальними людьми 50+** (мінімум 2 живі сесії, розділ 17.5) — ще не проведено.
- **Складання й розповсюдження production/preview-збірки (EAS Build)** для встановлення поза розробницьким середовищем — ще не зроблено.
- **Стабільність завантаження фотокадрів** на реальних Android-пристроях варто ще раз перевірити наживо після виправлень адреси сервера (`PUBLIC_BASE_URL`) — під час розробки була знайдена й виправлена причина, чому кадри інколи не доходили до сервера, але повторна перевірка на живому телефоні бажана.
- Юридичні тексти (Умови використання, Політика конфіденційності) — прості сторінки-заглушки, фінальний юридичний текст на 4 мовах не готовий.

### Критерії приймання (Definition of Done) — без змін по суті, з поправкою на фото

1. Дитина реєструється (телефоном або поштою), створює план і запрошення.
2. Батько/мати реєструється (будь-яким із двох способів), вводить код, потрапляє в сім'ю.
3. Батько/мати виконує 4 вправи з фотокадрами. Четверта вправа нараховує ставку дня.
4. Дитина бачить статус у реальному часі, отримує push (за наявності toku), переглядає кадри.
5. Повторний виклик зарахування вправи не подвоює нарахування.
6. Дитина створює переказ; батько/мати підтверджує; належна сума зменшується.
7. Пропущений день фіксується протягом години після півночі й перериває серію.
8. Кадри старше 7 днів видаляються.
9. Видалення акаунта чистить усі дані, включно з кадрами.
10. Усе працює на iOS і Android, мовами uk / ru / pl / en.

Пункти 1–3, 5–9, 10 (крім живого пристрою з push) перевірені під час розробки автоматизованими сценаріями. Пункт 4 (push) і повна перевірка на реальних пристроях — залишаються відкритими, як зазначено вище.

## 19. Правила для AI-агента

Цей розділ — інструкція для AI-асистента, який пише код. Оновлено відносно v3.0: правила про Supabase/RLS/RPC замінені на еквіваленти для NestJS-бекенду.

**Загальні**

1. Це **єдине джерело правди**: цей файл. Якщо є розбіжність із попередніми версіями ТЗ, слідувати цьому документу.
2. Не додавати функцій і бібліотек, яких немає в розділах 2 і 3, без явної причини в коміті чи документації.
3. Працювати **вертикальними зрізами**: одна фіча від бекенду до екрана, потім перевірка. Не робити «спочатку всі екрани».
4. Не імітувати AI-верифікацію фото: ніяких фейкових екранів «ІІ аналізує фото».

**Безпека та гроші**

5. **Гроші й нарахування рахуються тільки на сервері**, у транзакційних методах сервісів (`WorkoutsService`, `LedgerService`). Клієнт нічого не додає до балансу.
6. Кожен ендпоінт, що читає чи змінює дані сім'ї, перевіряє належність користувача до цієї сім'ї в коді сервісу (немає декларативних RLS-політик — перевірка explicit).
7. Жодних секретів у мобільному застосунку чи репозиторії. Ключі Twilio, Resend, JWT, підпису сховища — лише у змінних середовища бекенду.
8. Кожен захищений ендпоінт перевіряє JWT через guard і, де потрібно, роль користувача.
9. Тимчасовий режим входу без коду (5.6) ніколи не вмикається за замовчуванням і завжди супроводжується голосним попередженням у логах, поки активний.

**Код**

10. TypeScript `strict` на обох сторонах.
11. Усі тексти через i18n (4 мови), без захардкоджених рядків.
12. Стилі лише через дизайн-токени (розділ 17.4). Іконки — лише через реєстр `Icon.tsx`, нових прямих імпортів з бібліотеки іконок в компонентах не робити.
13. Анімації — лише через наявні примітиви (`Reveal`, `FadeView`, `PopIn`, `PressableScale`), не через вбудовані `entering`-анімації Reanimated (ламають розкладку на вебі, перевірено на практиці).
14. Емодзі — лише для аватарів сім'ї й вибору ролі; для решти інтерфейсу — векторні іконки.
15. Дати рахувати у часовому поясі батька/матері; у базі зберігати UTC.
16. Малі файли, один компонент — одна відповідальність. Серверні дані через TanStack Query.
17. Зміни схеми бази — лише новою міграцією TypeORM, і міграція має бути ідемпотентною (безпечно застосовується повторно чи на частково зміненій базі) — реальний випадок із пілоту, коли ручне втручання в базу частково застосувало зміну, і звичайна міграція впала б.

**Перевірка**

18. Камеру, push, SMS і листи перевіряти на реальному провайдері хоча б раз перед релізом (не лише консольними провайдерами розробки).
19. Для зарахування вправи, створення переказу, закриття прострочених днів — e2e-тести на реальній PostgreSQL (ідемпотентність, межі сум, чужа сім'я).
20. Перед завершенням фічі: перевірити чек-лист із розділу 18 і всі чотири мови.
21. Перевіряти застосунок з чистого встановлення пакетів (`npm ci`) і чистою збіркою (`tsc`, `eslint`) перед тим, як вважати задачу завершеною.

| Юридична сторона грошей | У v1 гроші не рухаються через застосунок. Перед v2 (автовиплата) обов'язково консультація з юристом і Stripe/BaaS: хто юридично тримає гроші |
| Фото з людиною | Оцінити з юристом, чи можуть вони вважатися даними про здоров'я (DPIA) — те саме питання, що було для відео у v3.0 |
| Довіра та шахрайство | У сімейному пілоті прийнятно (дитина сама дивиться фото); у масштабі потрібна перевірка |
| Розрахунки на чесному слові | Дитина може не переказати, батько/мати може не підтвердити. Це предмет дослідження пілоту |
| Юридичні тексти | Умови та Політика на 4 мовах — фінальний текст ще не готовий |
| Вартість SMS і листів | Ліміти й гео-обмеження в Twilio; обмеження провайдера Resend без домену; слідкувати за витратами при переході на реальних користувачів |
| Push на Android/iOS | FCM/APNs облікові дані для EAS — потребують перевірки на реальній production-збірці |
| Публікація в магазинах | Ще не почата (потрібні EAS Build production-профіль, скріншоти, опис). Для App Store потрібне видалення акаунта в застосунку (вже реалізовано) |
| Живе тестування з людьми 50+ | Ще не проведене — критично важливий крок перед висновками пілоту (розділ 1.4) |

## 21. Глосарій

| Термін | Значення |
|---|---|
| **Сім'я** | Пара «дитина + батько/мати» з власним планом, ставкою та балансом |
| **День (сесія)** | Запис про запланований день занять сім'ї |
| **Ставка** | Сума винагороди за повністю виконаний день |
| **Належить (owed)** | Зароблено мінус підтверджені перекази |
| **Переказ (settlement)** | Запис про грошовий переказ від дитини, що потребує підтвердження батьком/матір'ю |
| **Серія (streak)** | Кількість запланованих днів поспіль зі статусом «виконано» |
| **Completion rate** | Частка виконаних днів від запланованих |
| **OTP** | Одноразовий код підтвердження — з SMS або з листа на пошту, однаковий механізм для обох |
| **Тимчасовий вхід без коду** | Режим лише для закритого тестування: вхід за номером зі списку без коду підтвердження (розділ 5.6) |
| **Фотокадр** | Один із 3 знімків, які батько/мати робить під час виконання вправи (замінює відеозапис із v3.0) |
| **Guard** | Перевірка в NestJS, що не пускає запит далі без дійсного JWT (аналог RLS-політики в термінах Supabase) |
| **StorageProvider** | Абстракція над сховищем фотокадрів: локальний диск або S3/R2 |
| **JWT** | Токен доступу; access-токен короткостроковий, refresh-токен оновлюється з ротацією |
| **EAS** | Expo Application Services, хмарна збірка й оновлення мобільного застосунку |
| **GDPR** | Загальний регламент ЄС про захист даних |
| **Railway** | Хмарна платформа, де розгорнутий бекенд і база даних |

# Відмінності реалізації від ТЗ v3.0

ТЗ v3.0 писалося під Supabase. Бекенд реалізовано на NestJS + PostgreSQL (Railway) за вибором замовника.
Продуктова логіка (розділи 1–11 ТЗ) НЕ змінюється; змінюється лише спосіб реалізації.

| ТЗ v3.0 (Supabase) | Реалізація тут |
|---|---|
| Supabase Auth (phone OTP) | `auth/`: `otp_codes` + Twilio/Console SMS + власні JWT + `refresh_tokens` з ротацією |
| Таблиця `profiles` (id = auth.users.id) | Таблиця `users` (id — власний uuid; телефон унікальний) |
| Таблиця `sessions` | Таблиця `day_sessions` (щоб не плутати з сесіями авторизації) |
| Таблиця `exercise_records` | без змін |
| `ledger_entries.status` = `confirmed \| pending \| rejected` | без змін; додано CHECK-обмеження на узгодженість `status`/`resolved_at` |
| RLS-політики | Guards (`JwtAuthGuard`, `RolesGuard`) + `FamilyContextService` (familyId завжди береться з сервера, ніколи з клієнта) |
| RPC-функції (`get_or_create_today`, `complete_exercise`, `create_settlement`, `resolve_settlement`) | Сервіси в транзакціях TypeORM: `DaySessionsService`, `ExerciseCompletionService`, `LedgerService` (блокування `FOR UPDATE`) |
| `pg_cron` (закриття днів, чистка відео) | `@nestjs/schedule`: `ClosePastDaysTask`, `PurgeVideosTask` |
| Supabase Storage + **відео 7 днів** | **Кадри замість відео (рішення замовника):** 3 JPEG на вправу, ключ `{familyId}/{sessionId}/{exerciseId}/{1..3}.jpg`, порт `StorageProvider` (local ↔ S3/R2), підписані URL, видалення через 7 днів |
| Supabase Realtime | socket.io gateway `/realtime` + події `session.updated`, `ledger.updated`, `family.updated`, `family.removed` |
| Edge Functions (push) | `NotificationsListener` + `PushService` (Expo Push) на доменні події |
| Видалення акаунта (Edge Function) | `AccountDeletionService` + каскади БД |

## Додатково до ТЗ (виникло під час проєктування схеми)

- `otp_codes`, `refresh_tokens` — таблиці авторизації.
- `invites.revoked_at` — нове запрошення знецінює попередні.
- `users.push_enabled`, `users.last_login_at` — перемикач сповіщень із профілю; аудит входу.
- `GET /families/current/parent-status` — окремий ендпоінт для дашборда дитини (стан «сьогодні», ліміт нагадування).
- `exercises.category` — enum замість вільного тексту.
- Гроші: `numeric(6,2)` / `numeric(8,2)` + `decimalTransformer`. Підсумки — лише SQL `SUM`; проміжні обчислення — в центах (`money.util.ts`).

## Інваріанти, які не можна порушувати

1. Баланс = `SUM(earn) − SUM(settlement confirmed)`. Клієнт ніколи не змінює баланс сам.
2. Один `earn` на день (унікальний частковий індекс) → нарахування ідемпотентне.
3. «День» = локальна дата батька/матері за його `timezone`; у БД лише UTC-мітки та дата без часу.
4. `rate` фіксується в `day_sessions` при створенні дня; зміни плану діють з наступного дня.
5. Відео видаляється через 7 днів; запис вправи залишається (`video_deleted_at`).
6. Усі мутації грошей — у транзакції з блокуванням рядка сім'ї.

## Кадри замість відео (v3.1)

- ТЗ §6.3, §7.4, §8.6: «запис відео» → «3 кадри під час вправи»; «Зарахувати без відео» → «Зарахувати без фото»; `video_*` → `photo_keys[]`, `photos_expires_at`, `photos_deleted_at`.
- API: `POST /workouts/uploads` приймає `frames[1..3]` і повертає `uploads[]`; `complete` приймає `photoKeys[]` (порожній = без фото); `GET /workouts/records/:id/photos` замість `/clip`.
- Коди помилок: `VIDEO_*`/`CLIP_*` → `PHOTO_KEY_INVALID`, `PHOTO_TOO_LARGE`, `PHOTO_TYPE_NOT_ALLOWED`, `PHOTOS_DELETED`, `PHOTOS_NOT_AVAILABLE` (+ `STORAGE_SIGNATURE_INVALID` для локального сховища).
- Демо-відео техніки вправ (`exercises.demo_video_url`) лишаються: це не відео користувачів.

## Автентифікація (реалізація)

- **Паролів немає** (ТЗ §5.4). «Відновлення доступу» = повторний вхід за номером і SMS на будь-якому пристрої; сесія 30 днів із ротацією refresh-токенів. Додатково: `POST /auth/logout-all` («вийти на всіх пристроях» при втраті телефона). Втрата самого номера в v1 вирішується через підтримку (лист із екрана входу).
- **Антишахрайство:** SMS лише на країни зі `SMS_ALLOWED_COUNTRIES` (за замовчуванням PL, UA; помилка `PHONE_COUNTRY_NOT_ALLOWED`). Той самий список — у Twilio Geo Permissions і в `mobile/src/constants/countries.ts`.
- **Порядок першого запуску** за ТЗ §5.1: згода → онбординг (3 слайди, «Пропустити») → країна й номер (підтвердження «Цей номер правильний?») → SMS-код → роль → ім'я → батько/мати: «Чекаємо на запрошення», дитина: створення запрошення (перший план налаштовується після приєднання, бо сім'я створюється при приєднанні).
- Після першого входу мова профілю = мова пристрою (uk/pl/en, інакше en), таймзона оновлюється при кожному вході.

## Правки після тестування (жовтень 2026)

- **Вибір мови — перший екран** застосунку (до згод і онбордингу); мова застосовується одразу й після входу записується в профіль. У сітці мов українська й російська — по діагоналі (не поруч).
- **Вхід через Google (Gmail):** `POST /auth/google { idToken }` — сервер перевіряє ID-токен через Google tokeninfo (`aud` ∈ `GOOGLE_CLIENT_IDS`, підтверджена пошта) і знаходить/створює акаунт за поштою (той самий, що й при вході кодом на цю пошту). `GET /auth/config` повертає `googleEnabled`. Застосунок: `EXPO_PUBLIC_GOOGLE_{WEB,ANDROID,IOS}_CLIENT_ID`.
- **«Фонд»** замість «Фонд на місяць»: спонсор поповнює фонд наперед на будь-який строк (`POST /ledger/fund-deposits`, таблиця `fund_deposits`, лише облік). Статистика: `fundDeposited`, `fundBalance` (поповнення − нарахування з моменту першого поповнення), `fundMonthlyCost`, `fundMonths`, `fundCoversUntil`. «Залишилось виплатити» → **«До виплати»**.
- **Підбір вправ ШІ** (`families.exercise_mode = 'ai'`, за замовчуванням для всіх сімей): детермінований планувальник `programs/ai-planner.ts` — фокус занять по черзі «силові → координація → розтяжка → дихальні» (4 заняття на тиждень = кожен вид раз на тиждень), розминка й заминка, ротація вправ виду по тижнях, різні групи рухів в одному дні, хвиля навантаження (0.9 · 1 · 1.15 · 1) поверх «Автоускладнення», без вправ на крокомір. План за замовчуванням: 4 дні на тиждень, 15 хв.
- **Вправи спонсора** (вкладка «Вправи» замість «Програми»): каталог розділами з мініатюрою руху, опис вправи з відео, галочка «включити в щоденні» (`families.selected_exercise_ids`, режим `manual`); без відмічених вправ у режимі `manual` день складається з активної програми. Призначення програми перемикає сім'ю в `manual`.
- **Довільний порядок вправ і пропуск:** усі невиконані вправи дня доступні (`state: current`), `EXERCISE_OUT_OF_ORDER` більше не повертається. `POST /workouts/:sessionId/exercises/:exerciseId/skip` — пропустити без оплати (`exercise_records.skipped`, `state: skipped`); день завершується, коли пройдено всі вправи.
- **ШІ-перевірка м'якша:** складніший різновид (віджимання від підлоги замість опори) зараховується; `isCorrect = false` не блокує при оцінці ≥ 65; людина має бути видна щонайменше в половині кадрів (було 2/3); порада «як виправити» має стосуватися саме названої проблеми. «Мертвий жук» перейменовано на «Прес лежачи: рука й протилежна нога» з чіткішим описом.
- **Автоускладнення:** темп до 100 % на тиждень (було до 15 %).
- **Літера «ё»** прибрана з усіх текстів (застосунок, seed-дані, CRM; у БД — міграцією).
- Шкали «Вплив на організм» тепер показують реальне значення (раніше смуга завжди була повною через помилку анімації ширини).

## Економія (жовтень 2026)

- **«Підбір вправ ШІ» токенів не витрачає** — це детермінований алгоритм на сервері (`programs/ai-planner.ts`), без мовної моделі.
- **AI-перевірка виконання** (єдине, за що платимо OpenAI, ≈ $0.01 за спробу) лишилась тією ж за точністю, але:
  - безкоштовна перевірка кадрів ДО виклику моделі (`ai/frame-precheck.ts`): камеру закрито / темно / у вправі з рухом кадр зовсім не змінюється → відмова без токенів;
  - не більше `AI_ANALYSIS.MAX_ATTEMPTS_PER_EXERCISE` (5) платних перевірок однієї вправи за день → `AI_ATTEMPTS_LIMIT`, застосунок пропонує «Пропустити без оплати».
- **Розмір застосунку:** голосові записи 12 МБ → 0.4 МБ (лишились лише фрази, які звучать: «вдих/видих», старт, відлік, фініш); ролики 35 МБ → 22 МБ (перекодовано H.264 ~700 кбіт/с без звукової доріжки; оригінали — `fit-app/video-originals/`, у застосунок не входять); векторна анімація-фігурка більше не потрапляє в бандл.

## Гроші (структура під v2, жовтень 2026)

Реалізовано за ТЗ §20.1 і макетом замовника; детально — `docs/PAYMENTS.md`. Поповнення фонду й автопоповнення — Stripe
(картка, Apple Pay, Google Pay, BLIK, PayPal); виплати батькам — Stripe Connect Express (BLIK для виплат Stripe не підтримує);
IAP App Store / Google Play — лише для підписки (передача реальних грошей між людьми через IAP заборонена правилами магазинів).
Без ключів усе вимкнено: застосунок показує облікове поповнення й «Переказ зроблено», як у v1.

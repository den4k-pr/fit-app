# Пошта: підтвердження кодом через Resend

Вхід і реєстрація за поштою — без паролів (ТЗ §5.4): адреса → лист із випадковим 6-значним кодом → код → (новий акаунт) роль → ім'я.
Правильно введений код доводить, що пошта належить людині: при першому вході акаунт створюється вже з **підтвердженою поштою**
(`users.email_verified_at`, у відповіді API `emailVerified: true`); кожен наступний вхід — так само з кодом.
Вхід через Google теж ставить пошту підтвердженою (Google віддає лише підтверджені адреси).

- Код діє 5 хвилин, одноразовий, повторно — через 60 с, не більше 5 запитів за 10 хв, після 5 помилок код анулюється.
- У БД лише HMAC-хеш коду. Сам код — тільки в листі (у логах його немає).
- **Тестових адрес із фіксованим кодом немає.** Входу без коду немає.

Відправка зроблена так само, як `MailService` в інших проєктах: офіційний SDK `resend` (`resend.emails.send`), ключ `RESEND_API_KEY`,
адреса відправника `MAIL_FROM` на своєму домені, брендований HTML-лист + текстова версія. Помилку Resend сервер не ковтає:
код у БД видаляється, клієнт отримує `OTP_SEND_FAILED`, а в лозі — причина й підказка, що виправити.

## Підключення домену (один раз)

1. resend.com → **Domains → Add Domain**. Краще піддомен, напр. `mail.your-domain.com` (репутація основного домену не страждає).
2. Resend покаже DNS-записи: **SPF** (TXT/MX на `send.mail…`), **DKIM** (TXT `resend._domainkey…`), рекомендовано **DMARC** (TXT `_dmarc…`, напр. `v=DMARC1; p=none;`).
   Додайте їх у DNS там, де керуєте доменом, і натисніть **Verify**. Статус має стати **Verified** (від хвилин до кількох годин).
3. **API Keys → Create API Key** (Sending access, можна обмежити цим доменом). Ключ починається з `re_`.
4. Railway → сервіс бекенду → Variables:

```
NODE_ENV=production
EMAIL_PROVIDER=resend
RESEND_API_KEY=re_...
MAIL_FROM=auth@mail.your-domain.com
MAIL_FROM_NAME=Книжка турботи
```

Листи йтимуть від «Книжка турботи <auth@mail.your-domain.com>». Старий `EMAIL_FROM` (повний рядок) працює, лише якщо `MAIL_FROM` не задано.
Видаліть застарілі змінні, якщо вони є: `OTP_TEST_EMAILS`, `OTP_TEST_NUMBERS`, `OTP_TEST_CODE`, `OTP_TEST_IN_PRODUCTION`, `OTP_DISABLED`, `LOGIN_ALLOWED_PHONES`.

## Перевірка після деплою

1. Лог старту: `✅ Пошта: Resend, відправник Книжка турботи <auth@…>`. Якщо там ⚠️ про `onboarding@resend.dev` — не задано `MAIL_FROM`.
2. У застосунку: «Пошта» → своя адреса → «Отримати код» → лист приходить у «Вхідні» (не «Спам»), код підходить.
3. Resend → **Emails**: лист зі статусом *Delivered* (id листа є в лозі сервера, `event:email_accepted id:…`).

## Що бачите в логах

| Рядок | Значення |
|---|---|
| `event:email_accepted provider:resend id:...` | Resend прийняв лист |
| `event:email_failed ... hint:...` | Resend відмовив; у `hint` — що виправити (ключ, домен, відправник) |
| `❌ EMAIL_PROVIDER=console у production` | листи не відправляються, вхід за поштою неможливий — увімкніть Resend |
| `❌ EMAIL_PROVIDER=resend, але немає RESEND_API_KEY` | не задано ключ |

## Локальна розробка

`EMAIL_PROVIDER=console` (за замовчуванням): лист не надсилається, його текст із кодом друкується в лозі сервера (`Лист НЕ відправлено`).
У production консольний провайдер відмовляє. В e2e-тестах (`NODE_ENV=test`) код читається з «вихідних» консольного провайдера.
